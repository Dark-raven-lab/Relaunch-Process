# Process Auto Relaunch

Утилита для Windows, изначально разработана для слежения за враппером Torch игры Space Engineers
она следит за выбранным процессом и автоматически перезапускает его при завершении или зависании. Умеет слать уведомления в Discord (webhook).

## Возможности

- Наблюдение за процессом по имени
- Автоперезапуск — сразу или с задержкой (таймер в секундах)
- Определение зависания по загрузке ЦПУ и отклику окна
- Принудительное завершение зависшего процесса (опционально)
- Перед завершением зависшего процесса — облегчённый дамп и managed-стеки потоков в `Dumps\<имя процесса>\` (хранятся 5 последних)
- Код выхода наблюдаемого процесса при его завершении. Код -1 при уже запущенной новой копии
  (плановый перезапуск) пишется только в файл лога; -1 без новой копии помечается как снятие извне
- Короткий журнал событий в интерфейсе программы (100 последних строк)
- Полный файловый лог в `Logs\<имя процесса>\Relauncher-yyyy-MM-dd.log`
- Уведомления в Discord через webhook
- Обновление из GitHub Releases по кнопке

## Установка и ручное обновление

1. Скачайте `Relaunch-Process-vX.Y.Z-x64.zip` со страницы [Releases](../../releases).
2. Распакуйте архив целиком в папку утилиты. Одного exe недостаточно: нужны все DLL и `Relaunch Process.exe.config`.
3. Запустите `Relaunch Process.exe`.

Чтобы обновить вручную, закройте утилиту, распакуйте новый архив в ту же папку с заменой файлов
и запустите её снова. Настройки (путь к программе, вебхук и остальное) переносятся в новую версию
автоматически, если папка утилиты не меняется. Папки `Logs` и `Dumps` сохраняются.

## Использование

1. Укажите имя процесса.
2. Выберите режим перезапуска — по таймеру или сразу.
3. При необходимости включите принудительное завершение зависшего процесса.
4. Включите наблюдение — дальше программа работает в фоне.
5. Для уведомлений настройте Discord webhook (URL, имя бота, аватар) в меню настроек.

## Обновление

Меню «Обновление» есть начиная с версии 1.7.2, автообновление — начиная с 1.7.5;
более старые версии обновляются вручную (см. выше).

```
Обновление
 ☑ Автоматически
   Проверить сейчас
```

**Проверить сейчас** проверяет последний опубликованный релиз на GitHub (черновики и pre-release
не предлагаются). Если он новее установленной версии, утилита показывает список изменений
и после подтверждения устанавливает его (порядок установки ниже).

**Автоматически** (по умолчанию выключено, состояние запоминается):

- через 5 минут после запуска утилиты и дальше раз в час проверяется последний релиз;
- релиз ставится не раньше чем через 5 часов после публикации — за это время неудачный релиз
  можно удалить с GitHub, и он не попадёт на серверы с автообновлением;
- ставится только в безопасный момент: наблюдаемый процесс запущен, нет отсчёта до его перезапуска,
  он не завис, и не открыто другое окно утилиты (если наблюдение выключено — в любой момент).
  Иначе установка откладывается до следующей проверки через час;
- окон не показывает: найденная версия и отложенная установка пишутся в лог, перезапуск и ошибки
  установки — в историю, лог и Discord. Если GitHub недоступен, ошибка пишется только в лог;
- после перезапуска новая версия сама включает наблюдение, если оно было включено,
  и пишет в Discord «Утилита обновлена до версии X».

Порядок установки (одинаковый для кнопки и автообновления):

1. Скачивает `Relaunch-Process-vX.Y.Z-x64.zip` и `.sha256` в папку `Updates` рядом с exe
   и сверяет SHA-256.
2. Проверяет архив: только файлы без папок, есть `Relaunch Process.exe` нужной версии, сборка x64.
3. Переименовывает свои файлы в `*.old`, кладёт на их место новые и запускает новую версию.
4. Ждёт до 60 с, пока новая версия подтвердит запуск (все DLL загружаются), и закрывается.
   Если подтверждения нет, новая версия завершается, старые файлы возвращаются и утилита
   продолжает работать на прежней версии.
5. Новая версия ждёт выхода старой, показывает окно и удаляет `*.old` и папку `Updates`.

Наблюдаемый процесс при обновлении не перезапускается. Пока идёт проверка и скачивание, наблюдение продолжается.
После обновления по кнопке наблюдение включится само, только если отмечено «Запоминать последнее состояние»;
после автообновления — всегда, если оно было включено.
Настройки переносятся в новую версию автоматически. Папки `Logs` и `Dumps` не трогаются.
Ход обновления пишется в лог `Logs\<имя процесса>\`.

Что нужно для работы кнопки:

- доступ в интернет к `api.github.com` (проверка релиза), `github.com` и `*.githubusercontent.com`
  (скачивание архива). Если сервер закрыт файрволом или прокси, кнопка покажет ошибку — обновите вручную;
- права на запись в папку утилиты.

Если обновление не удалось:

- утилита пишет причину в историю, лог и Discord и продолжает работать на прежней версии;
- папка `Updates` с остатками попытки может остаться — она удаляется при следующей попытке;
- если новая версия запустилась, но упала до показа окна, файлы `*.old` остаются рядом с exe:
  удалите новые файлы и уберите у `*.old` суффикс `.old`, чтобы вернуть прежнюю версию,
  либо обновите вручную из архива нужного релиза.

## Выпуск релиза

Релизы собираются автоматически через GitHub Actions ([.github/workflows/release.yml](.github/workflows/release.yml)).
Версия задаётся только в `Properties/AssemblyInfo.cs`, тег вручную ставить не нужно.

При каждом push в `master` workflow читает `AssemblyInformationalVersion`:

- если тега `v<версия>` на GitHub ещё нет, он собирает конфигурацию Release x64, создаёт тег
  на этом коммите и публикует архив `Relaunch-Process-vX.Y.Z-x64.zip` на странице [Releases](../../releases);
- если такой тег уже есть (версию не поднимали), сборка пропускается.

Порядок выпуска:

1. Поднимите версию в `Properties/AssemblyInfo.cs`:
   - `AssemblyInformationalVersion` задаёт версию релиза, например `1.7.2`;
   - `AssemblyVersion` и `AssemblyFileVersion` имеют вид `1.7.2.MMDD`, например `1.7.2.1112`.
2. Закоммитьте изменения в `master` и отправьте ветку:
   ```
   git push origin master
   ```
3. Ход сборки виден на вкладке Actions. Через 2–4 минуты релиз с архивом появится в Releases,
   описание изменений составляется из коммитов автоматически. Чтобы получить новый тег локально,
   выполните `git fetch --tags`.

Важно:

- Любой push в `master` с новой версией сразу публикует релиз. Чтобы отправить изменения без релиза,
  не поднимайте версию.
- Утилиты с включённым автообновлением поставят релиз через 5–6 часов после публикации.
  Если релиз неудачный, удалите его с GitHub раньше.
- Все три версии должны начинаться одинаково: `AssemblyInformationalVersion` вида `X.Y.Z`,
  `AssemblyVersion` и `AssemblyFileVersion` вида `X.Y.Z.N`. Иначе сборка останавливается с ошибкой
  и релиз не создаётся.
- Тег создаётся только после успешной сборки. Если сборка упала, исправьте ошибку и сделайте
  новый push или запустите workflow вручную: Actions → Release → Run workflow.
- Имя архива `Relaunch-Process-vX.Y.Z-x64.zip` и файл `.sha256` рядом с ним использует обновление
  из утилиты. Если их переименовать или убрать из workflow, кнопка «Обновление» перестанет работать.
- В архив попадает всё содержимое `bin\x64\Release`, кроме `.pdb`. Утилите нужны все DLL из архива
  (ClrMD для стеков зависшего процесса, Newtonsoft.Json для Discord), копировать один exe нельзя.
- Если релиз получился неправильным, удалите его вместе с тегом (Releases → Delete, затем
  `git push origin --delete vX.Y.Z` и `git tag -d vX.Y.Z`), исправьте и сделайте push
  или запустите workflow вручную.

Локальная сборка: `msbuild "Process Auto Relaunch.csproj" -restore -p:Configuration=Release -p:Platform=x64`.
Post-build шаг кладёт zip в папку `bin`.
